## 엘라스틱서치
### 1. 검색 시스템
- 검색엔진: 데이터를 색인하고 검색하는 프로그램 (elasticsearch가 여기에 해당)
- 검색 시스템: 검색엔진을 기반으로 만든 전체 시스템
  - 수집기: 웹이나 DB에서 데이터를 모음
  - 스토리지: 데이터를 저장
  - 색인기: 형태소 분석기로 텍스트를 쪼개 역색인 구조로 저장
  - 검색기: 사용자가 입력한 검색어도 같은 방식으로 쪼갠 뒤, 유사도 점수로 문서를 찾아 순위를 매김

### 2. RDB와 다른 점
- RDB는 Like 검색 시 단순 문자열 매칭이라 동의어나 단어 변형을 처리하지 못함
- ElasticSearch는 역색인을 씀. 책 뒤의 "찾아보기"처럼 단어마다 그 단어가 들어 있는 문서 목록을 저장해 두는 방식
  - 인덱스↔테이블, 샤드↔파티션, 문서↔행, 필드↔열, 매핑↔스키마, Query DSL↔SQL

### 3. 장단점
- 장점:
  - 오픈소스, REST API와 JSON으로 다루기 때문에 언어에 상관없이 사용 가능
  - 스키마 없이도 저장 가능
  - 확장성과 가용성이 높음

- 단점: 
  - 준실시간으로 데이터를 색인한 뒤 보통 1초가 지나야 검색이 됨
  - 트랜잭션과 롤백이 없음
  - 업데이트 비용이 큼
    - 수정하면 내부적으로 기존 문서를 삭제하고 새 문서를 다시 색인

### 4. 클러스터와 노드
- 마스터 노드: 클러스터를 관리
- 데이터 노드: 실제 데이터와 샤드를 갖고 검색-집계를 수행
- 코디네이팅 노드: 요청을 받아 다른 노드에 분배하고 결과를 합침
- 인제스트 노드: 색인 전에 데이터를 전처리합니다.

### 5. 실무 팁
- 스키마리스(자동 매핑)는 피하는 게 좋음
  - 이 필드는 Nori로 잘라라 라고 직접 설정해야 됨
  - "아버지가 방에 들어가신다."를 기본 분석기로 색인하면 아버지가 통째로 하나의 토큰이 됨.
  - 아버지로 검색해도 이 문서가 나오지 않음 -> 한국어는 형태소 분석기를 매핑에 직접 지정해야 함. 매핑은 한 번 만들면 바꿀 수 없어서 바꾸러면 다시 색인해야 함
    - 아버지가 / 방에 / 들어 / 가신다.
    - 저장된 조각에는 '아버지'가 없고 '아버지가'만 있음 그래서 아버지로 검색하면 못 찾음 
      - 여기서 Nori같은 한국어 형태소 분석기를 사용해야 됨
- text: 형태소 분석이 필요한 검색용 필드
- keyword: 정확한 일치, 정렬, 집계용 필드
- 문서 id는 자동 UUID 대신 DB의 PK와 맞춰 두는 게 좋음
  - 그래야 나중에 DB와 동기화 하거나 업데이트 시 편함
  - 엘라스틱은 직접 지정하지 않으면 랜덤 문자열이 붙음 db에서 수정했을 때 엘라스틱이 랜덤 문자열이라 알 수 없음
- 검색은 URI 방식보다 Request Body(Query DSL)방식을 실무에서 주로 사용
